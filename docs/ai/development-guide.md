# 开发任务指南

适用于新功能、跨系统或架构调整。遵循[根规则](../../AGENTS.md)，从[项目上下文](project-context.md)定位本项目真实设计与目录。

## 开始与范围

先确认目标行为和来源，再阅读相关设计、代码、场景、资源及调用方。缺失文档不等于可以自行改玩法。
优先交付可运行的完整小流程，不先生成所有空壳服务或管理器。
复杂任务明确输入输出、所有权、生命周期、失败恢复、适用测试及排除范围；简单修改只需简短说明。
用户已授权的常规技术选择自行推进。重要未决选择只阻塞相关部分，其余独立工作继续。

## 实施原则

- 复用当前架构，明确哪些对象拥有状态以及谁可修改；避免 UI、动画和存储各自维护一套规则。
- 内容配置与运行时状态区分；数据源保持一致，避免多个可编辑副本漂移。
- 按项目需要管理持久化、随机数、网络和异步行为，不把与当前任务无关的复杂机制提前引入。
- 修改公开接口和持久字段时检查所有调用方、场景绑定、资源和兼容性。
- 代码格式与中文注释按[编码规范](coding-standards.md)，不沿用已有难读代码作为新代码模板。
- 不为让实现或测试通过而偷偷修改玩法来源、删除断言或吞掉错误。

## 迭代安排

按项目实际情况组织：环境和最小启动 → 核心可玩流程 → 系统整合 → 内容与交互完善 → 导出和试玩修订。
这不是强制阶段名，也不说明当前项目已经完成其中任何阶段。
美术可并行准备共用组件和代表性素材；程序用可辨识占位推进，素材批量扩产前先做引擎样例验证。
保存与恢复、测试和资源导出随相关功能逐步验证，不能全推迟到最终交付。
复杂项目已有排期时沿用其依赖和任务 ID，不另建一份竞争性状态表。

## 交付

按[测试指南](testing-guide.md)执行适用检查，按[文档指南](documentation-guide.md)同步直接受影响的事实。
按[Git 指南](git-guide.md)判断完整改动的提交时机并主动进行本地提交，报告真实提交结果或未提交原因。
引擎工具创建成功不等于功能验收；检查实际节点和引用，并运行适用场景。
需要委派时读[子代理指南](subagent-guide.md)，最终说明实际修改、证据、未验证部分和剩余事项。
