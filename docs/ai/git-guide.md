# Git 协作与提交指南

适用于项目文件修改后的交付，以及暂存、提交、分支和版本历史操作。遵循[根规则](../../AGENTS.md)。
用户于 2026-10-19 授权代理自行判断何时进行本地提交；本指南落实该授权，不要求每次提交前重新确认。
用户当前明确要求的提交范围、分支或“暂不提交”等约束优先。

## 提交时机

以完整的逻辑改动为提交单位，不以对话轮次、编辑次数、文件数量或固定时间间隔决定。
满足以下条件时主动创建本地提交，并在交付中报告结果：

- 已完成一个有独立目的、可审查和可回退的改动，如功能、修复、规范文档或资源接入。
- 该改动所需的调用方、场景、资源、测试和文档已同步，不依赖尚未纳入的文件才能成立。
- 已执行[测试指南](testing-guide.md)要求的适用检查，真实结果支持该提交的完成范围；纯文档改动无需启动游戏。
- 差异与暂存内容已核对，可将本任务改动和用户已有工作安全区分，且不含禁止提交的内容。

| 情况 | 处理 |
| --- | --- |
| 小型修复或文档调整已完整完成并检查 | 通常合为一次提交，不因改动小而一直不提交 |
| 较大任务已有独立完成、验证过的步骤 | 在这些边界分次提交，保持每次改动完整；相关集成检查仍须执行 |
| 同一目的涉及脚本、场景、资源与 UID | 作为完整改动提交，不能拆成引用暂时失效的状态 |
| 仍在试错、必需检查未执行或相关验证失败 | 继续处理，不默认提交为完成状态；已知基线问题说明依据与影响 |
| 仅咨询、只读评审或没有实际文件差异 | 不创建空提交，不为产生提交而修改文件 |
| 用户明确要求保存 WIP 或未完成检查点 | 按其范围处理，消息和交付标明未完成内容及未通过的检查 |

不把“尚未推送”当作无限堆积本地改动的理由，也不把每一行调整拆成单独提交。
需要试验或高影响修改时，可先提交已经完成并验证的独立部分；不能顺手提交用户已有的未完成工作来充当备份。

## 开始前确认

- 用 `git rev-parse --show-toplevel` 确认真实仓库根目录，避免在错误目录或无关的父仓库中操作。
- 核对当前分支、`git status --short --branch`、工作区差异、暂存区差异及未跟踪文件，记录本任务开始前已有的改动。
- 有既定分支或工作树时沿用；只有确需隔离时才创建本地分支或工作树，不默认切换、删除或覆盖用户分支。
- 不根据默认习惯猜测主分支名、远程名称或远程地址；本地提交不要求存在远程仓库。
- 当前目录不是 Git 仓库时，继续完成已授权的文件工作并报告无法提交；仓库初始化需用户要求或已有明确项目决定。

## 暂存与提交前检查

1. 查看实际差异和文件清单，确认文件来自本任务且内容与授权目标一致。
2. 执行相应文档、解析、行为或场景检查；修复本次引入的问题，保留真实验证结论。
3. 使用明确路径或选定差异块暂存，如 `git add -- <已核对路径>` 或 `git add -p -- <已核对路径>`；这些是示意命令，需替换实际路径。
4. 核对 `git diff --cached --stat` 与 `git diff --cached`，并执行 `git diff --cached --check`；核对新增、删除、重命名与二进制文件，不能只看统计。
5. 确认暂存区恰好覆盖本次提交范围，再创建提交。失败时先检查实际状态与原因，不重复盲目执行。

- 不默认执行 `git add .`、`git add -A` 或 `git commit -a`；整批纳入前必须逐项核实范围。
- 用户已有暂存内容不自动属于本任务；暂存区存在无关改动时，不直接提交整个暂存区，也不重置它来方便操作。
- 同一文件混有本任务与他人改动时，审查到差异块并安全隔离；无法可靠区分就暂不提交该部分，保留现场并说明限制。
- 不为清理工作区自动执行 stash、checkout、restore、reset 或 clean；只提交能够安全界定的完整改动，其余工作继续。
- 检查忽略规则和实际文件内容，不提交密钥、令牌、用户存档、日志、临时输出、`.godot/` 缓存或本机专属路径。
- Godot 源素材、`.tscn`、`.tres`、必要的 `.import` 设置及脚本／着色器 `.uid` 文件随实际资源一起维护；不能因属于引擎生成文件就一概忽略。
- 使用现有 `.gitattributes` 与 `.gitignore`，不顺带改全仓换行或重新导入素材；大型二进制和 Git LFS 沿用已有约定，不擅自迁移历史。

## 提交消息

沿用已有清晰的项目约定；没有既定约定时使用 `类型(范围): 中文说明`，范围可省略。
常用类型为 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`，准确表达改动性质，不把功能缺失包装成重构。

- 标题简短说明具体变化，例如 `docs(ai): 统一 GDScript 编码规范` 或 `docs(ai): 明确自主提交时机与检查要求`。
- 较复杂的提交正文说明原因、最终行为和必要影响；适用时写明已执行的验证与限制，不堆砌逐文件流水账。
- 不用“更新”“修改一些问题”等含混消息，也不写未经验证的“全部通过”“已发布”或虚构的关联任务编号。
- 不伪造作者、签名或共同作者；身份缺失时说明情况，不自动修改全局 Git 配置。

## 提交后与授权边界

- 提交成功后核对 `git log -1 --oneline`、`git show --stat --oneline HEAD` 与 `git status --short`，确认真实提交 ID、范围和剩余改动。
- 不要求工作区必须完全干净；用户原有改动和本任务明确暂缓的部分应保留，交付时说明相关剩余事项。
- 默认通过新提交修正问题，不自行 amend、rebase、reset 或改写已有历史；钩子、签名或身份检查失败时不通过跳过检查来掩盖问题。
- 自主本地提交不自动授权 push、远程分支删除、合并、创建发布标签或发布版本；这些动作根据用户对应授权执行。
- 权限、身份、钩子、仓库状态或其他环境条件使提交不可执行时，保留已完成文件与检查结果，明确报告未提交及原因；规则不能突破工具权限。
- 最终报告列出提交 ID 和简要目的；未提交则说明原因，不把暂存、工具调用成功或已写好消息当成提交成功。
